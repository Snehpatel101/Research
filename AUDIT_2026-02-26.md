## 3. Label Imbalance — Root Cause Analysis

### The Distribution

| Horizon | Long (+1) | Neutral (0) | Short (-1) | Long % |
|---------|-----------|-------------|------------|--------|
| H5 | 24,661 | 710,140 | 214,666 | **2.6%** |
| H10 | 68,067 | 519,078 | 362,317 | 7.2% |
| H20 | 147,547 | 300,571 | 501,334 | 15.5% |

### Root Cause: Transaction Cost Asymmetry

**File:** `src/data/labeling/triple_barrier.py:382`

```python
k_up_effective = k_up + cost_in_atr   # Upper barrier widened by cost
# k_down is NOT adjusted
```

The transaction cost adjustment only penalizes the **upper barrier** (long/win), making label=+1 structurally harder to achieve. With symmetric raw barriers (k_up=k_down=1.20 for H5), the effective barriers become:

- Upper (long win): `1.20 + cost_in_atr` ≈ 1.35-1.50
- Lower (short win): `1.20` (unchanged)

This creates a ~12-25% asymmetry that cascades into extreme class imbalance.

**File:** `src/data/pipeline/config/barriers_config.py:168-173` (MGC H5 config)

### What Exists for Mitigation

| Mitigation | Status | File |
|-----------|--------|------|
| Class weights (balanced) | Active | `xgboost_model.py:159-164` |
| SMOTE / oversampling | **Not implemented** | N/A |
| Label rebalancing | **Not implemented** | N/A |
| Barrier optimizer (Optuna) | Exists but doesn't account for cost asymmetry | `optimization.py:421-430` |

### Class Weight Problem

At H5, balanced weights produce: Long = **12.83x**, Short = 1.47x, Neutral = 0.45x. The 28.8:1 long-to-neutral weight ratio destabilizes gradient boosting — the loss is dominated by the rare class.

### Recommendations

1. **Drop H5 entirely**, or restructure to binary classification
2. **Apply transaction cost to BOTH barriers symmetrically** at `triple_barrier.py:382`
3. **Use H20 as primary horizon** (most balanced: 53/32/16)
4. **Consider binary classification**: "significant move" vs "no move" instead of 3-class

## 4. XGBoost Early Stopping Failure

### The Bug

3 of 5 walk-forward windows ran to the full 500 rounds without early stopping. The root cause is a parameter interaction:

- `learning_rate = 0.05` (slow convergence, tiny improvements each round)
- `early_stopping_rounds = 20` (patience resets on any micro-improvement)
- Result: val loss keeps improving by epsilon, patience never expires

**File:** `src/models/boosting/xgboost_model.py:124` — `"early_stopping_rounds": 20`
**File:** `src/models/boosting/xgboost_model.py:120` — `"learning_rate": 0.05`

### Config Drift Bug

Three sources define XGBoost defaults with **conflicting values**:

| Parameter | `xgboost_model.py` (active) | `model_configs.py` (unused) | `global.yaml` |
|---|---|---|---|
| `learning_rate` | **0.05** | 0.1 | Not set |
| `early_stopping_rounds` | **20** | 50 | Not set |
| `n_estimators` | 500 | 500 | Not set |

The `xgboost_model.py:get_default_config()` values are the ones that run. `model_configs.py:XGBoostConfig` is dead config.

### Walk-Forward Key Mismatch Bug

**File:** `src/models/training/modes/walk_forward.py:436`

```python
_model_config["early_stopping_patience"] = getattr(...)  # WRONG KEY
```

XGBoost reads `early_stopping_rounds`, not `early_stopping_patience`. Pipeline-level patience config never reaches boosting models. This is a latent bug.

### Recommendations

| Fix | File:Line | Change |
|-----|-----------|--------|
| Tighten early stopping | `xgboost_model.py:124` | `early_stopping_rounds: 20 → 10` |
| Or raise learning rate | `xgboost_model.py:120` | `learning_rate: 0.05 → 0.1` |
| Fix key mismatch | `walk_forward.py:436` | Add `_model_config["early_stopping_rounds"]` alongside |
| Clean up dead config | `model_configs.py:127-141` | Align with `xgboost_model.py` or remove |

## 5. TCN Receptive Field Mismatch

### The Warning

```
WARNING: Receptive field (61) < sequence length (120).
Consider adding more layers or increasing kernel_size.
```

### The Math

**File:** `src/models/neural/tcn_model.py:141-148`

```
Config: 4 layers, kernel_size=3, dilation_base=2

rf = 1
Layer 0: dilation=1,  +2*(3-1)*1  = +4,   rf = 5
Layer 1: dilation=2,  +2*(3-1)*2  = +8,   rf = 13
Layer 2: dilation=4,  +2*(3-1)*4  = +16,  rf = 29
Layer 3: dilation=8,  +2*(3-1)*8  = +32,  rf = 61
```

**Receptive field = 61.** The TCN cannot see timesteps 1-59. Those 59 timesteps are noise that dilutes the global average pooling output.

### Memory Waste

| Metric | seq_len=120 (current) | seq_len=64 (fixed) | Savings |
|--------|----------------------|-------------------|---------|
| X_train size | 949K × 120 × 42 × 4 = **19.1 GB** | 949K × 64 × 42 × 4 = **10.2 GB** | **8.9 GB** |
| Per-fold slice | ~15.3 GB | ~8.2 GB | ~7.1 GB |

### Where seq_len=120 is Hardcoded (4 locations)

| File | Line | Current |
|------|------|---------|
| `src/models/neural/tcn_model.py` | 211 | `"sequence_length": 120` |
| `src/models/config/data_requirements.py` | 219 | `sequence_length=120` |
| `src/core/contracts/model_contract.py` | 352 | `sequence_length=120` |
| `src/data/pipeline/config/feature_sets/definitions.py` | 369 | `default_sequence_length=120` |

### Recommendations

**Option A (recommended):** Change all 4 locations to `sequence_length=64` (power-of-2 for GPU alignment, > receptive field of 61). Saves ~9 GB RAM, eliminates wasted timesteps.

**Option B:** Add a 5th layer (`num_channels=[64,64,64,64,64]`), increasing receptive field to 125. Costs 25% more compute and parameters. Only worthwhile if 10 hours of history (120 × 5min) genuinely adds signal vs 5 hours (64 × 5min).

## 6. CPU RAM vs GPU RAM — Memory Architecture Issue

### The Pattern

The entire dataset lives in CPU RAM as numpy arrays. The GPU only processes tiny batches:

```
CPU RAM                                          GPU
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━      ━━━━━━━━━━━
Feature Engineering (pandas)    ~1.4 GB
3D Reshape .copy()             +19.1 GB
Scaling (creates copy)         +19.1 GB (temp)
PreparedData X_train           ~19.1 GB
DataLoader batches ──────────────────────────▶   ~26 MB per batch
                                                  Model params ~50 MB
                                                  ━━━━━━━━━━━
Peak CPU: ~40-55 GB                              Peak GPU: ~200 MB
```

### Key Bottlenecks

| Stage | What Happens | CPU RAM Cost | File:Line |
|-------|-------------|-------------|-----------|
| 3D reshape | `sliding_window_view().copy()` | **19.1 GB** | `sequence.py:231` |
| Scaling | Creates copy during transform | **19.1 GB** temp | `scaling.py:326` |
| predict() | `torch.tensor(X).to(device)` | **19.1 GB** extra copy | `base_rnn.py:612` |
| OOF fold | Slices ~80% of 3D array per fold | **~15 GB** per fold | `oof_sequence.py` |
| DataLoader pin_memory | Locks tensor in page-locked RAM | Prevents swapping | `base_rnn.py:727` |

## 7. predict() Memory Bug — All 9 Neural Models

### The Bug

Every neural model's `predict()` uses `torch.tensor()` (which **copies** the entire array) instead of `torch.from_numpy()` (which **shares** memory). Then it moves the **entire dataset** to GPU at once, even though it then loops through in batches.

**File:** `src/models/neural/base_rnn.py:612`
```python
# BAD: creates full copy on CPU + moves ALL to GPU
X_tensor = torch.tensor(X, dtype=torch.float32).to(self._device)
```

Note: `_create_dataloader` (line 708) was correctly fixed to `torch.from_numpy()` in Phase 78, but `predict()` was never fixed.

### Affected Files

| File | Line | Pattern | Memory Waste (949K rows) |
|------|------|---------|--------------------------|
| `base_rnn.py` | 612 | `torch.tensor(X).to(device)` — all at once | ~19 GB CPU copy + ~19 GB GPU |
| `lstm_model.py` | 162 | `torch.tensor(X).to(device)` — all at once | ~19 GB CPU copy + ~19 GB GPU |
| `gru_model.py` | 170 | `torch.tensor(X).to(device)` — all at once | ~19 GB CPU copy + ~19 GB GPU |
| `tcn_model.py` | ~350 | `torch.tensor(X).to(device)` — all at once | ~19 GB CPU copy + ~19 GB GPU |
| `nbeats_model.py` | 676 | `torch.tensor(X).to(device)` — all at once | ~19 GB CPU copy + ~19 GB GPU |
| `inceptiontime_model.py` | 481 | `torch.tensor(X).to(device)` — all at once | ~19 GB CPU copy + ~19 GB GPU |
| `resnet1d_model.py` | 508, 561 | `torch.tensor(X).to(device)` — all at once | ~19 GB CPU copy + ~19 GB GPU |
| `patchtst_model.py` | 432 | `torch.tensor(X).to(device)` — all at once | ~19 GB+ (4D) |
| `itransformer_model.py` | 471 | `torch.tensor(X).to(device)` — all at once | ~19 GB+ (4D) |
| `tft_model.py` | 655, 787 | `torch.tensor(X).to(device)` — all at once | ~19 GB+ (4D) |

### The Fix (One-Line Per File)

```python
# BEFORE (copies everything):
X_tensor = torch.tensor(X, dtype=torch.float32).to(self._device)

# AFTER (zero-copy, batch to GPU):
X_tensor = torch.from_numpy(np.ascontiguousarray(X))
# Then batch .to(device) inside the prediction loop
```

**Impact:** Saves ~19 GB of CPU RAM per predict() call across all neural models.
