# Program Alignment Blueprint (How to Make the Factory “Snap Together”)

This document translates the *intended program* (as written in root docs like `CLAUDE.md` and `ARCHITECTURE_FLOW_MAP_ASCII.md`) into a concrete set of contracts that the repo can consistently implement.

It focuses on alignment, not rewriting: how to make the existing Phase 1 pipeline, Phase 2 training, Phase 3 CV/OOF, and serving/bundling behave like one cohesive factory.

---

## 1) The Actual Program You’re Describing (Canonical)

You want a robust ML factory where **one uploaded dataset** becomes a **timeframe fanout**, and then each model chooses a **dataset view** per run:

### 1.1 Market-Data Fanout (timeframe datasets)

Input:
- One canonical raw OHLCV dataset per symbol (typically `data/raw/{SYMBOL}_1m.parquet` or `.csv`)

Output:
- A set of derived timeframe datasets (your “nine datasets”), e.g.:
  - `1m, 5m, 10m, 15m, 20m, 25m, 30m, 45m, 1h`

### 1.2 Per-Model Dataset Views (per run, configurable)

Each model chooses one of the following strategies (per run, per model):

- **Single timeframe only**
  - model trains on `TF_primary` only, no MTF indicators, no multi-stream ingestion.
- **Single timeframe + higher timeframe indicators**
  - model trains on `TF_primary`, but features include indicators derived from one or more `TF_context[]`.
- **Multi-timeframe ingestion (multi-stream)**
  - model ingests multiple timeframes simultaneously (e.g., 3 TF streams: `1m + 5m + 15m`).

### 1.3 Ensembles (heterogeneous by design)

Ensembles should be able to combine base models trained on:
- different timeframes,
- different feature strategies,
- different data representations (2D tabular vs 3D seq vs multi-stream).

Meta-learners then consume OOF predictions, not raw features.

## 2) Current Reality (What the Program Actually Does Today)

This section intentionally uses the repo’s *actual* entrypoints and defaults.

### 2.1 Entrypoints that matter

- Pipeline: `./pipeline` → `src/pipeline_cli.py` → `src/cli/*`
- Training: `scripts/train_model.py` (restored) + `scripts/train_ensemble.py` (restored)
- CV/OOF: `scripts/run_cv.py` (restored)
- Serving: `scripts/serve_model.py` (restored) wrapping `src/inference/*`

### 2.2 Where Phase 1 outputs really go

The pipeline is run-scoped:
- `runs/{run_id}/data/...` (clean/features/labels/splits/scaled/datasets)

But multiple docs/scripts still default to global paths:
- `data/splits/scaled` (as if it were a single shared “current dataset”)

That mismatch is the single biggest “program alignment” failure: Phase 2/3 tools don’t naturally consume Phase 1 outputs without manual `--data-dir` pointing.

## 3) The Contracts Needed to Make Everything Align

If you define these contracts (even just as documentation first), the codebase can be organized around them.

### Contract A — MarketDataStore (fanout)

One pipeline run produces a “store” of timeframes:

- `MarketDataStore(run_id, symbol)`
  - `timeframes: list[str]` (e.g., 9 TFs)
  - `base_timeframe` (canonical input TF; usually `1min`)
  - `paths[timeframe]` → pointers to cleaned OHLCV and optional derived artifacts

**Minimum required artifacts per timeframe**
- Cleaned OHLCV (for that TF)

**Optional artifacts per timeframe**
- Engineered features (for that TF)
- Labels (for that TF; must define what horizons mean)
- Splits + scaling artifacts (for that TF)

### Contract B — DatasetView (per model)

Training does not point at “a folder”; it requests a view:

- `DatasetView`
  - `primary_timeframe`
  - `mtf_strategy: none | indicators | ingestion`
  - `mtf_timeframes: list[str]` (context or streams)
  - `feature_set` (model-family selection)
  - `sequence_length` and windowing config (if sequential)
  - `label_horizon_policy` (bars vs time; must be explicit)

### Contract C — RunLinking (traceability)

Training runs must always declare their provenance:

- training run references:
  - `pipeline_run_id`
  - `dataset_view` used (fully serialized)
  - `feature_set` resolved list (not just the alias)
  - `horizon(s)` used

CV runs must reference:
- `pipeline_run_id`
- list of base model training configs or direct dataset views (if CV trains models itself)

Bundles must reference:
- training run id
- preprocessing graph / feature column contract

## 4) Alignment Decisions You Must Make (and document once)

### 4.1 What do label horizons mean across timeframes?

Today horizons are “bars ahead”. If you run the same horizon on 1m vs 1h, it is a different time horizon.

You must choose one:
- **Horizon = bars** (simple, but not comparable across TFs), or
- **Horizon = time** (needs conversion to bars per TF; best for multi-TF factory).

### 4.2 Where is the “default dataset” pointer?

If you keep `data/splits/scaled` as a convenience default, define it as:
- a symlink or copy to a chosen `runs/{run_id}/data/splits/scaled`, OR
- a “latest successful run” pointer generated by the pipeline.

Otherwise, all training/CV scripts should accept `--run-id` and resolve paths internally.

### 4.3 When are MTF indicators computed?

Two valid approaches:

- **Precompute MTF indicators inside Phase 1** (materialize them into the primary TF dataset)
  - faster training runs, larger datasets.
- **Compute MTF indicators as a DatasetView transform** (on demand per model)
  - more flexible, but must be cached and reproducible.

You can mix these, but only if the contract states which is used and how caching works.

---

## 5) Concrete Alignment Checklist (Docs-level “Definition of Done”)

The program is aligned when all of the following are true:

1. One command can produce the timeframe fanout and write a manifest enumerating those datasets.
2. Every training run can specify per-model views (TF + strategy) without manual file-path fiddling.
3. Heterogeneous ensembles can intentionally combine:
   - different TFs,
   - different view strategies,
   - different model families,
   and train a meta-learner on OOF predictions.
4. Every artifact is traceable:
   - bundle → training run → pipeline run → raw dataset.
